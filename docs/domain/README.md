# 도메인 개요

이 폴더는 찜꽁의 **도메인 모델** — 이 서비스가 다루는 개념들이 각각 무엇이고, 서로
어떤 관계이며, 어떤 규칙이 그 관계를 지탱하는지 — 를 설명한다.

코드의 구조나 실행 방법은 루트의 [AGENTS.md](../../AGENTS.md)에 있다. 여기서는
"왜 이 개념이 이렇게 생겼는가"만 다룬다.

## 한 문장

찜꽁은 **사용자가 붙여넣은 링크에서 실제로 방문할 수 있는 장소를 뽑아내
지도에 꽂아 두는 서비스**다.

도메인 전체가 그 문장에서 파생된다. 링크는 장소의 *출처*이고, 장소는 링크의 *결과*이며,
사용자는 그 둘을 **가리키는 찜**을 소유한다 — 링크도 장소도 아니라는 점이 중요하다.

## 도메인 지도

```
                   ┌──────────────┐
                   │    Member    │  사람 하나
                   └──────┬───────┘
                          │ 소유
        ┌─────────────────┼─────────────────┐
        │                 │                 │
  ┌─────▼──────┐   ┌──────▼──────┐   ┌──────▼──────┐
  │AuthIdentity│   │   Bookmark  │   │   Session   │
  │ 소셜 로그인 │   │   내 찜 하나 │   │ 로그인 브라우저│
  └────────────┘   └──────┬──────┘   └─────────────┘
                          │ 참조 (+BookmarkMemo)
                   ┌──────▼──────┐
                   │     Post    │  전역 공유 — 게시물 하나
                   └──────┬──────┘
                          │ PostPlace (+position)   └─► Author  전역 공유
                   ┌──────▼──────┐
                   │    Place    │  전역 공유 — 특정 사용자의 것이 아니다
                   └─────────────┘
```

**소유의 경계가 곧 도메인의 핵심 구분선이다.** `Bookmark`는 사용자의 것이고
`Post`·`Author`·`Place`는 아무의 것도 아니다. 이 비대칭이 이 도메인에서 가장 자주
오해받는 지점이며, [aggregates.md](aggregates.md)와
[invariants.md](invariants.md)가 그 이유를 다룬다.

**그 선이 예전에는 한 칸 위에 있었다.** `Post`와 `Bookmark`는 `SavedPost` 하나였고,
그래서 소유자가 있는 값과 없는 값이 한 행에 섞여 있었다 — 같은 릴스를 붙여넣는
사용자마다 크롤링·LLM·지오코딩을 다시 지불해서 이미 다른 행에 있는 값에 도달했다.
지금은 두 번째 사용자의 저장이 `Post`를 **읽기만** 한다.

## 두 개의 하위 도메인

찜꽁은 성격이 전혀 다른 두 하위 도메인으로 나뉜다.

**인제스트 (핵심 도메인)** — 링크에서 장소를 만들어 낸다. 이 서비스가 존재하는
이유이자 경쟁력이 있는 부분이고, 동시에 **전부 외부 시스템에 의존하는** 부분이다
(인스타그램·유튜브·LLM·네이버 지역검색). 그래서 이 도메인의 규칙은 대부분
"외부가 실패했을 때 무엇이 참인가"를 정의한다.

**게시물당 정확히 한 번만 돈다.** 그 한 번의 결과가 `Post`이고 그 행은 불변이다 —
외부에 의존하는 도메인에서 같은 질문을 두 번 묻지 않는 것이 곧 차단당하지 않는
방법이다.

**신원 (지원 도메인)** — 누가 무엇을 소유하는지 정한다. 제품 차별점은 없지만
틀리면 남의 데이터가 새는 부분이다. 여기의 규칙은 대부분 "무엇을 믿지 않는가"를
정의한다 — 클라이언트가 보낸 좌표도, 제공자가 말한 전화번호 인증도 믿지 않는다.
