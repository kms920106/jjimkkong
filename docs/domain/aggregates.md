# 애그리거트 경계

이 도메인에서 "무엇이 함께 살고 함께 죽는가", 그리고 "무엇이 누구의 것인가".

## 세 개의 애그리거트

```
  ① 사람 (UserProfile)              ② 저장한 링크 (SavedPost)      ③ 장소 (Place)
  ─────────────────────             ────────────────────────       ──────────────
  UserProfile        [루트]          SavedPost          [루트]       Place   [루트]
   ├ AuthIdentity                     └ SavedPostPlace  (+메모)
   └ Session                                  │
                                              └──────────────────────► 참조만
```

**① 사람** — `UserProfile`이 루트. `AuthIdentity`와 `Session`은 사람 없이 존재할
이유가 없고, 사람이 사라지면 함께 사라진다(`onDelete: Cascade`). 로그인·탈퇴·
계정 병합은 전부 이 애그리거트 안의 일이다.

**② 저장한 링크** — `SavedPost`가 루트. `SavedPostPlace`는 링크에 붙은 값이지
독립적으로 조회하는 대상이 아니다. 링크가 지워지면 연결도 지워진다.

**③ 장소** — `Place`가 루트이며 **아무에게도 속하지 않는다.** ②가 ③을 참조할 뿐
소유하지는 않는다.

## 왜 Place는 따로 서 있는가

`Place`는 "지도 위에 실재하는 장소"를 모델링한 것이지 "사용자가 가진 항목"이
아니다. 그래서:

- **두 사람이 같은 카페를 저장하면 `Place` 행은 하나다.** `[name, address]`가
  유일 키이기 때문이다.
- **그 행은 누구의 것도 아니므로 아무도 고칠 수 없다.** 저장 시 이미 존재하는
  행은 `update: {}`로 upsert한다 — 다른 사람의 게시글도 그 행을 가리키고 있어서,
  덮어쓰면 남의 핀이 움직인다.
- **메모는 `Place`가 아니라 `SavedPostPlace`에 있다.** 메모는 장소의 속성이
  아니라 *이 게시글에서 이 장소를 저장한 나의* 속성이기 때문이다.

이 설계의 대가는 명확하다: **사용자가 장소 정보를 수정할 방법이 없다.** 이름이나
좌표가 틀렸다면 고칠 수 있는 건 네이버뿐이다. 이건 버그가 아니라 선택이며,
"사용자별 장소 편집"을 넣으려면 `SavedPostPlace`에 오버라이드 필드를 두거나
사용자 소유의 별도 엔티티를 만들어야 한다 — `Place`를 직접 고치게 만들면 안 된다.

## 애그리거트 간 규칙

**한 트랜잭션은 하나의 애그리거트만 바꾸는 게 원칙이지만, 이 코드베이스는
두 곳에서 의도적으로 어긴다.**

**1. 링크 저장 — ②와 ③을 한 트랜잭션에서 쓴다**
([posts/route.ts](../../frontend/src/app/api/posts/route.ts))

`Place` upsert와 `SavedPostPlace` 생성이 같은 트랜잭션 안에 있다. 나누면 장소만
만들어지고 연결이 실패한 고아 행이 남는다. 대신 **동시성 규칙이 하나 붙는다**:

> 장소를 `[name, address]` 순으로 **정렬한 뒤** upsert한다.

동시에 실행되는 두 트랜잭션이 겹치는 `Place` 집합을 건드릴 때 락을 같은 순서로
잡게 하기 위해서다. 정렬을 빼면 데드락이 난다.

또 하나:

> 재저장은 **덧붙이기가 아니라 교체**다.

`SavedPostPlace`를 전부 지우고 다시 만든다. 다시 인제스트했을 때 장소가 줄어들면
남아 있던 연결이 고아가 되기 때문이다.

**2. 탈퇴 — ①의 모든 하위를 한 트랜잭션에서 바꾼다**
([account/route.ts](../../frontend/src/app/api/account/route.ts))

`UserProfile.withdrawnAt`, `AuthIdentity.withdrawnAt`, `Session` 삭제가 한
트랜잭션이다. 반쪽만 적용되면 두 방향 모두 손상이다 — 프로필만 탈퇴되면
identity가 제공자 id를 계속 점유해 재가입이 막히고, identity만 풀리면 프로필이
아직 살아 있는 계정으로 응답한다.

## 소유권은 애플리케이션이 검사한다

**Prisma는 테이블 소유자로 접속하므로 Postgres RLS를 우회한다.** DB가 소유권을
지켜 주지 않는다는 뜻이다. 그래서 모든 라우트 핸들러가:

1. `requireUser()`를 호출하고
2. 반환된 `userId`로 쿼리를 한정한다

```ts
// 이 자체가 소유권 검사다
deleteMany({ where: { id, userId } })

// 이렇게 줄이면 그 행이 모든 사용자에게 열린다
delete({ where: { id } })
```

`SavedPost`와 `Session`, `AuthIdentity`는 `userId`를 갖고 있으므로 이 패턴이
그대로 적용된다. **`Place`에는 적용되지 않는다** — 소유자가 없기 때문이다.
그래서 `Place`를 보호하는 건 소유권 검사가 아니라 **"클라이언트가 보낸 좌표를
절대 믿지 않는다"**는 규칙이다([invariants.md](invariants.md) 참고).

## 애그리거트가 아닌 것

**`PhoneVerification`은 어느 애그리거트에도 속하지 않는다.** 아직 사람이
확정되지 않은 시점에 만들어지기 때문이다 — 이 행이 생길 때는 그 번호가 신규
가입인지 기존 계정 병합인지 모른다. `userId`가 없고 `phoneHash`와 `purpose`만
있는 이유가 그것이다. 수명이 짧고(만료), 성공하면 소비된다.
