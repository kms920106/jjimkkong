# 인제스트 도메인 — 링크가 장소가 되는 과정

이 서비스의 핵심 도메인. 사용자가 붙여넣은 링크 하나를 지도 위의 핀으로 바꾼다.

## 도메인 모델

인제스트는 **하나의 값이 네 번 변태하는 과정**이다. 각 단계의 값은 앞 단계보다
확실하고, 마지막 단계에서만 저장 가능하다.

```
  URL 문자열          "https://instagram.com/reel/abc?igsh=..."
      │  classifyUrl + canonicalize
      ▼
  분류된 링크          { platform: INSTAGRAM, url: ".../reel/abc/" }
      │  fetchMetadata
      ▼
  PostMetadata        { title, caption, thumbnail, author, needsManualCaption }
      │  extractPlaces  ← LLM
      ▼
  PlaceCandidate[]    [{ name: "대림창고", hint: "성수동" }]   ← 좌표 없음. 주장.
      │  geocodeCandidates  ← 네이버 지역검색
      ▼
  GeocodedCandidate[] [{ name, address, lat, lng, matched: true }]  ← 사실
      │  사용자 확인 + POST /api/posts (서버가 재지오코딩)
      ▼
  SavedPost + Place   저장됨
```

**핵심 성질: 마지막 화살표 직전까지 아무것도 저장되지 않는다.** `POST /api/ingest`는
읽기 전용이고, 사용자가 결과를 보고 확인해야 `POST /api/posts`가 쓴다.
LLM은 틀릴 수 있고 지도 검색도 엉뚱한 곳을 집을 수 있으므로, **사람이 최종 판정자**다.

## 받아들이는 링크

| 종류 | 예 | Platform |
|---|---|---|
| 인스타그램 post/reel | `instagram.com/reel/…`, `/p/`, `/reels/`, `/tv/` | `INSTAGRAM` |
| 유튜브 watch/shorts | `youtube.com/watch?v=…`, `/shorts/…`, `youtu.be/…` | `YOUTUBE` |
| 네이버 지도 장소 | `map.naver.com/p/entry/place/…`, `naver.me/…` | `NAVER` |
| 카카오 지도 장소 | `place.map.kakao.com/…`, `kko.to/…` | `KAKAO` |

**그 외는 전부 400이다.** 화이트리스트인 이유는 파이프라인의 모든 단계가
플랫폼별 지식(어디서 캡션을 읽는지, 어떤 UA를 써야 하는지)에 의존하기 때문이다.
모르는 사이트는 처리할 방법이 없지 잘 처리하지 못하는 게 아니다.

## 정규화가 도메인 규칙인 이유

`canonicalize()`는 편의 기능이 아니다. `SavedPost`의 유일 키가
`[userId, sourceUrl]`이므로 **정규화가 곧 "같은 게시글"의 정의**다.

- 인스타그램의 한 게시글은 `/p/`, `/reel/`, `/reels/`, `/tv/` 네 경로로 도달
  가능하다 → 하나로 수렴시키지 않으면 같은 게시글이 최대 네 행이 된다.
  (그리고 `/reels/<code>/`는 실제로 404이므로, 저장되는 링크는 살아 있는
  퍼머링크여야 한다.)
- 지도 링크도 공유 시트·모바일·데스크톱이 서로 다른 경로를 준다 → 숫자 id를
  뽑아 정규 진입 URL로 접는다.
- 트래킹 파라미터(`?igsh=`, `?si=`)는 떨어진다 → 같은 링크를 두 번 공유하면
  파라미터가 달라진다.

## 두 개의 분기: 게시글이냐 지도 링크냐

**이것이 인제스트 도메인에서 가장 중요한 구분이다.**

> **게시글은 장소를 *언급*하고, 지도 링크는 장소를 *지목*한다.**

게시글(인스타·유튜브)은 여러 장소를 자연어로 흘리듯 말한다. 어느 단어가 장소인지
판단이 필요하고, 그래서 LLM이 있다.

지도 링크는 장소 하나를 정확한 이름으로 가리킨다. **제공자가 이미 정답을
알려줬으므로 모델이 그걸 다시 쓰게 둘 이유가 없다.** `metadata.ts`가 og 태그에서
이름을 읽어 `place` 필드에 담고, 인제스트 라우트는 `extractPlaces()`를 건너뛰고
곧장 지오코딩한다.

이름을 읽는 자리는 벤더마다 다르다:

| | 이름 | 주소 |
|---|---|---|
| 네이버 | `og:description` | — |
| 카카오 | `og:title` | `og:description` (도로명, 지오코딩 힌트로 사용) |

네이버의 `og:title`은 항상 `네이버지도`라는 고정 문자열이다. 여기서 이름을 읽으면
모든 네이버 링크가 같은 장소가 된다.

## 1단계: 캡션 가져오기 (`metadata.ts`)

이 단계의 도메인 규칙은 전부 **"본문을 못 가져왔을 때 무엇이 참인가"**에 관한 것이다.

**유튜브** — `YOUTUBE_API_KEY`가 있으면 Data API v3를 쓴다. **설명 전문을 얻을
수 있는 유일한 경로**이고, 크리에이터가 장소를 실제로 나열하는 곳이 거기다.
키가 없으면 oEmbed로 떨어지는데 제목·작성자만 오므로 `needsManualCaption: true`가
된다. 즉 **키 없이도 동작하지만 유튜브는 항상 수동 입력**이다.

**인스타그램** — 브라우저 UA에는 캡션 없는 로그아웃 셸을 200으로 돌려준다.
크롤러 UA(`facebookexternalhit`)만 진짜 내용을 받는다. `embed/captioned/`를 먼저
시도하고 실패하면 `og:description`으로 간다 — 거기엔 캡션이 통째로 들어 있지만
앞에 인게이지먼트 껍데기가 붙는다:

```
46K likes, 361 comments - handle on May 16: "여기 진짜 맛있어요…"
                                             └── parseOgCaption()이 이것만 남긴다
```

**실패는 구체적인 `FailureReason`으로 로깅한다.** 조직적 차단, 셀렉터 파손,
타임아웃은 각각 정반대의 대응을 요구한다 — 차단이면 기다려도 안 되고, 셀렉터
파손이면 코드를 고쳐야 하고, 타임아웃이면 그냥 재시도다. 하나의 경고로 뭉뚱그리면
어느 쪽인지 알 수 없다.

**둘 다 비면 `needsManualCaption: true`.** 이건 에러가 아니라 **사용자에게 넘기는
분기**다. UI가 `CaptionPrompt`를 띄우고, 사용자가 붙여넣은 캡션은 **권위를 갖는다** —
그 값을 넣는 이유가 바로 자동 수집이 실패했기 때문이므로, 다시 가져오려 시도하지
않는다.

## 2단계: 장소 이름 추출 (`extract.ts`)

LLM이 캡션에서 "방문 가능한 장소"만 골라낸다.

**추출 대상**: 식당, 카페, 바, 상점, 숙소, 관광지, 전시·공연장 — 지도에서 찾아
실제로 갈 수 있는 곳.

**제외 대상**: 브랜드·제품명, 메뉴 이름, 인물·계정 이름, 해시태그, 그리고
`서울`·`제주`처럼 **넓은 행정 구역만 단독으로** 언급된 경우.

마지막 항목이 도메인 판단이다. "서울"은 장소지만 *방문할 수 있는 한 지점*이 아니다.
핀을 꽂을 수 없는 것은 이 도메인에서 장소가 아니다.

**제공자 교체 가능성이 이 모듈의 설계 제약이다.** OpenAI 호환
`/chat/completions` 엔드포인트면 무엇이든 동작하고, `LLM_API_KEY` /
`LLM_BASE_URL` / `LLM_MODEL`만 바꾸면 **코드 수정 없이** 제공자가 바뀐다.
이 성질을 깨뜨리지 말 것. 그 결과로 붙은 방어가 몇 개 있다:

- **`strict` json_schema를 걸어도 Zod로 다시 검증한다.** 갈아끼운 제공자가
  `response_format`을 무시할 수 있기 때문이다.
- **JSON 파싱이 관대하다.** 프로즈나 마크다운 펜스로 감싸 보내는 제공자를
  견딘다.
- **에러 처리가 상태 코드별로 다르다.** 5xx와 타임아웃은 재시도하고,
  429는 재시도하지 않는다 — 할당량은 몇 초 안에 풀리지 않으므로 재시도가
  무의미하다. `LlmRateLimitedError`가 429와 할당량 안내 문구로 표면화된다.

**같은 장소가 캡션에 두 번 나와도 한 번만 나온다** (이름 소문자 기준 dedupe).

## 3단계: 좌표 붙이기 (`geocode.ts`)

네이버 지역검색이 이름을 좌표로 바꾼다.

**순차 호출이다. 병렬이 아니다.** 네이버는 하나의 client id에서 몰아치는 요청을
거부한다. 게시글 하나당 후보가 많지 않으므로 지연 예산 안에 들어온다.

**힌트를 붙인 질의를 먼저 시도한다.** `성수동 대림창고` → 실패하면 `대림창고`.
같은 이름이 여러 동네에 있을 때 힌트가 정답을 가른다.

**`mapx`/`mapy`는 WGS84 도 단위에 1e7을 곱한 값이다** (`1270276368` → `127.0276368`).
옛 문서는 KATECH 투영이라고 하지만 이 엔드포인트는 더 이상 그 형식을 주지 않는다.

**결과의 두 실패 상태를 구분한다:**

| | 뜻 | 사용자에게 |
|---|---|---|
| `matched: false` | 검색은 됐는데 그런 장소가 없다 | "지도에서 찾지 못했어요" |
| `lookupFailed: true` | 검색 자체가 실패했다 (타임아웃/5xx/할당량) | "잠시 후 다시 시도해 주세요" |

**절대 합치지 말 것.** 전자는 사용자가 이름을 고치거나 포기해야 하고, 후자는
그냥 다시 누르면 된다. 하나로 뭉치면 재시도하면 되는 상황에서 사용자가 포기한다.

**후보는 최대 20개로 자른다** (`MAX_PLACES`). 후보 하나당 네이버 호출이 최대
두 번이므로, 긴 캡션 하나가 공유 client id 할당량을 다 태우는 걸 막는다.
`POST /api/posts`의 상한과 같은 값이어야 한다.

## 4단계: 저장 (`POST /api/posts`)

**여기서 도메인의 가장 중요한 보안 규칙이 나온다.**

> **클라이언트가 보낸 좌표는 절대 믿지 않는다.**

요청 본문에서 받는 건 **이름과 지역 힌트, 그리고 메모뿐**이다. 좌표·주소·카테고리는
서버가 다시 지오코딩해서 얻는다.

이유는 `Place`가 전역 공유이기 때문이다. `[name, address]`가 키이므로, 클라이언트가
lat/lng을 그대로 보낼 수 있으면 **한 사용자가 다른 사용자의 핀을 옮길 수 있다.**
재지오코딩은 그 행이 언제나 서버가 유도한 값만 담게 만든다.

같은 이유로 이미 있는 `Place` 행은 `update: {}`로 upsert한다 — 다른 게시글도
그 행을 가리키고 있으므로 덮어쓰면 안 된다.

**매칭된 장소가 하나도 없으면 422로 저장을 거부한다.** 장소 없는 저장은 이
도메인에서 의미가 없다 — 지도에 아무것도 안 올라가는 링크는 이 서비스가 하는
일을 안 한 것이다.

**두 질의가 같은 네이버 레코드로 수렴할 수 있으므로** `SavedPostPlace` 생성 전에
placeId 중복을 거른다. 안 그러면 `[postId, placeId]` 기본키가 충돌한다.
