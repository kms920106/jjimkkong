# 불변조건

**깨지면 데이터가 손상되거나 남의 데이터가 새는 규칙들.** 각 항목은 "무엇이
참이어야 하는가"와 "깨졌을 때 무슨 일이 일어나는가"로 되어 있다.

코드를 고치기 전에 이 목록에서 그 코드가 지키고 있는 규칙이 있는지 확인할 것.

---

## 소유권

### I1. 모든 API 라우트는 `requireUser()`로 시작하고 결과를 `userId`로 한정한다

**왜** — Prisma는 테이블 소유자로 접속하므로 Postgres RLS를 우회한다. DB가
소유권을 지켜 주지 않는다.

**깨지면** — `delete({ where: { id } })`처럼 `userId`를 빼면 그 행이 **모든
사용자에게 조용히 열린다.** 에러도 안 나고 로그도 안 남는다.

```ts
deleteMany({ where: { id, userId } })   // 이 자체가 소유권 검사다
delete({ where: { id } })               // 이 행은 이제 전 세계의 것이다
```

### I2. 클라이언트가 보낸 좌표는 절대 저장하지 않는다

**왜** — `Place`는 사용자 간 공유이고 `[name, address]`가 키다.

**깨지면** — 한 사용자가 요청 본문의 lat/lng으로 **다른 사용자의 핀을 옮길 수
있다.**

`POST /api/posts`가 받는 건 이름·힌트·메모뿐이고, 좌표는 서버가 다시 지오코딩한다.

### I3. 이미 존재하는 `Place` 행은 `update: {}`로 upsert한다

**왜** — 그 행은 다른 게시글, 다른 사용자의 것이기도 하다.

**깨지면** — 새로 저장한 사람의 지오코딩 결과가 이미 저장된 모두의 핀을 덮어쓴다.

### I4. 클라이언트의 `signedIn` 플래그는 권한이 아니다

**왜** — UI를 고르는 값일 뿐이다.

**깨지면** — 이걸 근거로 서버 검사를 생략하면 인증 없이 API가 열린다.

## 탈퇴와 유일성

### I5. 세 곳의 `withdrawnAt: null` 필터는 함께 움직인다

| # | 위치 | 빠지면 |
|---|---|---|
| 1 | `requireUser()` / `getUser()` | 탈퇴 계정이 그대로 정상 로그인 상태가 된다 |
| 2 | `linkProviderIdentity()`의 identity 조회 | 탈퇴 계정이 재방문 로그인으로 세션을 받는다 |
| 3 | `attachIdentity()` 트랜잭션 안의 owner 조회 | 재로그인이 탈퇴 계정을 되살린다 |

**왜** — 탈퇴는 소프트 삭제라서 **행이 남아 있다.** 하드 삭제라면 조회가 그냥
실패하겠지만, 여기서는 이 필터가 유일한 방어선이다.

### I6. `phoneHash`와 `[provider, providerUserId]`의 unique는 partial이어야 한다

```sql
WHERE "withdrawnAt" IS NULL
```

**왜** — 탈퇴 행이 전화번호와 제공자 id를 그대로 들고 있다.

**깨지면** — 전역 unique로 되돌리면 **탈퇴한 사용자가 영구히 재가입 불가**가 된다.

**주의** — Prisma 스키마 언어로 표현할 수 없어서 **마이그레이션 raw SQL에만
있다.** 스키마에는 `@unique`가 아니라 `@@index`가 적혀 있고, 그건 실수가 아니다.

### I7. 전화번호 조회는 `findFirst` + `withdrawnAt: null`이다

**왜** — I6의 결과. `findUnique`는 컴파일이 깨지는데, 그것도 의도된 것이다.

### I8. `AuthIdentity.withdrawnAt`은 `UserProfile.withdrawnAt`과 같은 트랜잭션에서 쓴다

**왜** — 비정규화된 값이다. partial unique index가 자기 테이블 컬럼만 읽을 수
있어서 필요하다.

**깨지면** — 반쪽만 적용되면 프로필은 탈퇴됐는데 identity가 제공자 id를 계속
점유해 재가입이 막히거나, 반대로 identity만 풀려 프로필이 살아 있는 계정으로
응답한다.

### I9. 고정 id를 upsert하는 코드를 만들지 않는다

**왜** — 탈퇴를 되돌릴 수 있는 유일한 형태가 그것이다. 예전 테스트 로그인이
정확히 그랬고, 그게 탈퇴 테스트 한 번에 모든 환경의 진입로가 막히는 걸 막는
장치였다.

**깨지면** — 그 구멍이 그대로 돌아온다.

계정은 반드시 **제공자 identity나 전화번호로** 찾을 것 — 둘 다 탈퇴 행을 건너뛴다.

### I10. 테스트 계정 로그인을 다시 만들지 않는다

**왜** — 인증되지 않은 누구든 한 번의 POST로 고정된 uuid가 될 수 있는 우회로였다.
"로컬에서만"이라는 의도로 들어와도 이 코드베이스에는 그걸 강제할 환경 분기가
없었고, **실제로 프로덕션 빌드에서도 켜져 있었다.**

로그인 흐름을 손으로 확인해야 하면 네이버 로그인 키와 Solapi 키를 채워서 진짜
경로로 들어갈 것.

## 전화번호

### I11. `phoneHash`와 `phoneEnc`는 항상 함께 쓰이고 함께 비워진다

**왜** — DB의 CHECK 제약(`("phoneHash" IS NULL) = ("phoneEnc" IS NULL)`)이
강제한다. `sealPhone()` 하나로 쌍을 만든다.

**깨지면**
- 해시만 있으면 → 주인에게 번호를 못 보여준다
- 암호문만 있으면 → 매칭이 안 돼서 그 사람은 다음 로그인에 **조용히 계정을
  하나 더 갖는다**

둘 다 상태가 아니라 **손상**이다.

### I12. `blindIndex()`에는 정규화된 `LocalMobile`만 넣는다

**왜** — branded 타입이 이걸 강제한다.

**깨지면** — 정규화되지 않은 문자열은 아무것도 매칭하지 않는 해시를 만들고,
그 실패는 **에러가 아니라 조용한 조회 실패**다.

### I13. `hashCode()`에는 평문 번호를 넘긴다 (blind index가 아니라)

**왜** — 평문을 쓰면 테이블 덤프만으로는 그 해시가 어느 번호에서 나왔는지 알 수
없다.

**깨지면** — blind index를 접으면 10^6짜리 코드 공간을 오프라인으로 갈아낼 수
있게 된다.

### I14. 복호화된 번호를 클라이언트로 보내지 않는다

`ProfileDTO.phoneMasked`는 **서버에서 이미 마스킹된 값**(`010-****-5678`)이다.
전체 번호는 브라우저에서 쓸 일이 없으므로 페이로드에 들어가서도 안 된다.

### I15. `v1:` / `v1.` 버전 표식을 떼지 않는다

**왜** — 키 회전은 아직 구현되어 있지 않고, 이 표식이 나중에 그걸 가능하게 하려고
있다.

### I16. `PHONE_ENCRYPTION_KEY`는 `AUTH_SECRET`과 분리되어 있다

**왜** — `AUTH_SECRET` 회전은 진행 중인 로그인만 잃지만,
`PHONE_ENCRYPTION_KEY`를 잃으면 **모든 계정이 SMS 재인증을 해야 한다.**

**길이 검사는 디코드한 바이트 수로 한다.** 문자 32개는 엔트로피 32바이트를
보장하지 않는다.

## 로그인

### I17. 첫 로그인은 예외 없이 SMS 인증을 거친다

**왜** — 제공자가 주는 번호는 그 계정 주인이 언젠가 등록해 둔 값일 뿐, **지금 이
로그인을 하는 사람이 그 번호를 쓸 수 있다는 증명이 아니다.**

`linkProviderIdentity()`에서 세션이 바로 나오는 경로는 **이미 연결된
`AuthIdentity`가 있는 재방문 하나뿐**이다.

**깨지면** — `phoneVerified` 같은 플래그를 다시 만들면 "제공자의 말로 가입을
통과시키는 경로"가 되살아난다.

### I18. `completeIdentityLink()`는 제공자가 준 번호를 쓰지 않는다

**둘이 일치할 때도 그렇다.** 저장되는 번호는 항상 SMS로 증명된 쪽이다.

### I19. SMS 발송 제한은 번호별과 로그인별 두 축을 모두 유지한다

**왜** — 번호별 제한만으로는 **한 로그인이 여러 번호로 퍼지는 걸 못 막는다.**
pending 쿠키는 TTL 10분 동안 의도적으로 재사용 가능하므로, OAuth 왕복 한 번으로
30초마다 새 번호에 문자를 보낼 수 있다.

**한쪽만 남기지 말 것.** 첫 로그인이 전부 이 경로를 지나면서 이 엔드포인트가
유일한 가입 경로가 됐다.

### I20. `phone/send`는 어떤 번호로 보낼지 제한하지 않는다

**왜** — 사용자가 번호를 고르고 그 번호를 증명하는 것이 설계다. 게이트는 문자
코드다.

**제공자가 준 번호와 대조하는 검사를 넣지 말 것** — 번호를 바꿔야 하는 정상
사용자를 막으면서 보안은 나아지지 않는다.

### I21. pending 로그인 쿠키는 두 장이고, 본문의 HMAC이 binding과 맞아야 열린다

**깨지면** — 본문 하나로 열리게 두면 공격자가 자기 로그인으로 쿠키를 만들어
피해자 브라우저에 심고, 피해자가 자기 번호로 인증을 마치는 순간 **공격자의
신원이 피해자 계정에 붙는다.**

### I22. `destroySession()`은 secret까지 확인하고 지운다

**왜** — id는 cuid라 추측 가능하다.

**깨지면** — 확인 없이 지우면 **남을 강제 로그아웃**시킬 수 있다.

### I23. 로그인 시 기존 세션을 먼저 파기한다 (세션 고정 방지)

### I24. `safeReturnPath()`는 파싱해서 확인하고, `startsWith` 블랙리스트로 되돌리지 않는다

**왜** — 막아야 하는 대상이 바로 `new URL()`이 문자열을 어떻게 재해석하는지다.

| 입력 | `startsWith` 검사 | 실제로 풀리는 곳 |
|---|---|---|
| `/\evil.com` | 통과 | `http://evil.com/` |
| `/<TAB>/evil.com` | 통과 | `http://evil.com/` |

파서는 authority 자리에서 `\`를 `/`와 같게 취급하고, C0 제어문자는 authority를
찾기 *전에* 떼어낸다.

**깨지면** — 로그인이 오픈 리다이렉트가 된다.

### I25. 페이지에 `requireUser()`를 넣거나 미들웨어를 되살리지 않는다

**깨지면**
- 페이지에 넣으면 → "로그인 없이 접속 가능"이라는 전제가 깨진다
- 미들웨어를 되살리면 → 세션이 만료된 `fetch()`가 401 대신 **로그인 페이지
  HTML**을 받아 `res.json()`이 깨진다

**유일한 예외는 `/verify-phone`** — 세션이 아니라 pending 쿠키를 요구하므로
이 원칙과 충돌하지 않는다.

## 인제스트

### I26. `matched: false`와 `lookupFailed: true`를 합치지 않는다

| | 뜻 | 사용자의 대응 |
|---|---|---|
| `matched: false` | 지도에 그런 장소가 없다 | 이름을 고치거나 포기 |
| `lookupFailed: true` | 검색이 일시적으로 죽음 | 다시 누르면 됨 |

**깨지면** — 재시도하면 되는 상황에서 사용자가 포기한다.

### I27. 지오코딩은 순차 호출이다

**왜** — 네이버는 하나의 client id에서 몰아치는 요청을 거부한다.

### I28. `Place` upsert는 `[name, address]` 순으로 정렬한 뒤 실행한다

**왜** — 동시에 실행되는 트랜잭션들이 겹치는 `Place` 집합의 락을 같은 순서로
잡게 한다.

**깨지면** — 데드락.

### I29. 재저장은 장소 집합을 덧붙이지 않고 교체한다

**왜** — 다시 인제스트했을 때 장소가 줄어들면 남아 있던 연결이 고아가 된다.

`SavedPostPlace`를 전부 지우고 다시 만든다.

### I30. `sourceUrl`은 정규화된 값이다

**왜** — `SavedPost`의 유일 키가 `[userId, sourceUrl]`이므로 **정규화가 곧
"같은 게시글"의 정의**다.

**깨지면** — 같은 게시글이 여러 행이 되어 중복 방지가 무의미해진다.
(그리고 인스타그램의 `/reels/<code>/`는 실제로 404이므로, 저장된 링크가
안 열리게 된다.)

### I31. 지도 링크는 LLM 추출을 건너뛴다

**왜** — 제공자가 이미 정확한 이름을 알려줬다. 모델이 다시 쓰게 두면 정답을
망칠 위험만 있다.

### I32. 네이버 지도의 이름은 `og:description`에서 읽는다

**왜** — `og:title`은 항상 `네이버지도`라는 고정 문자열이다.

**깨지면** — 모든 네이버 링크가 같은 장소가 된다.

### I33. LLM 응답은 `strict` json_schema를 걸어도 Zod로 다시 검증한다

**왜** — `LLM_BASE_URL`로 갈아끼운 제공자가 `response_format`을 무시할 수 있다.

### I34. 제공자 교체 가능성을 깨뜨리지 않는다

`LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL`만 바꾸면 **코드 수정 없이**
제공자가 바뀌어야 한다. 특정 제공자의 응답 형식이나 헤더를 하드코딩하지 말 것.

### I35. LLM 재시도는 5xx·타임아웃만, 429는 재시도하지 않는다

**왜** — 할당량은 몇 초 안에 풀리지 않는다.

### I36. 인스타그램 실패는 구체적인 `FailureReason`으로 로깅한다

**왜** — 조직적 차단, 셀렉터 파손, 타임아웃은 각각 정반대의 대응을 요구한다.
하나의 경고로 뭉뚱그리면 어느 쪽인지 알 수 없다.

### I37. 사용자가 붙여넣은 캡션은 권위를 갖는다

**왜** — 그 값을 넣는 이유가 자동 수집이 실패했기 때문이다.

**깨지면** — 다시 가져오려 시도하면 이미 차단 중인 소스에 대고 타임아웃 예산만
태운다.

## 문구

### I38. UI에 "모두 삭제"라고 쓰지 않는다

**왜** — 데이터는 남는다. 사용자에게 거짓말이 된다.

약속할 수 있는 건 **"다시 볼 수 없고 재로그인 시 새 계정으로 시작한다"**뿐이다.

### I39. 사용자에게 보이는 문자열은 전부 한국어, 코드·주석·식별자는 영어

### I40. 에러는 `toErrorResponse()`를 거친다

**왜** — 알려진 에러 클래스를 상태 코드로 매핑하고 나머지는 전부 일반적인 500
뒤로 감춘다.

라우트에서 제각각 에러 형태를 만들지 말고 여기에 분기를 추가할 것.

## 주석

### I41. 코드를 고칠 때 그 코드의 주석도 함께 고친다

**왜** — 이 코드베이스의 주석은 *왜*를 설명하며, 대개 **어렵게 알아낸 외부
동작을 기록한 것**이다.

**깨지면** — 다음 사람이 그 주석이 막고 있던 버그를 다시 만들어 넣는다.
