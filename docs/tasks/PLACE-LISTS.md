# 즐겨찾기(장소 리스트) — 구현 노트

네이버지도 "저장"의 스크린샷 12장(`IMG_1106…1117.PNG`)을 이 앱에 옮긴 것. 대상은
**장소(`Place`)**이고 링크(`Bookmark`)가 아니다 — 찜은 이미 "링크를 저장한다"를 맡고 있으므로
역할이 겹치지 않는다.

## 무엇이 생겼나

```
지도 핀 탭 → PlaceSheet의 ★ → 리스트 선택 시트 → 저장
                                 └ 새 리스트 만들기(이름·색상·공개범위·메모·URL)

/lists              내 리스트 목록
/lists/<내 순번>     리스트 상세 + 지도
/u/<memberId>       남의 공개 리스트 목록   — 전체 공개만
/u/<memberId>/<순번> 발견 가능한 주소       — 전체 공개만
/s/<token>          공유 링크로 여는 주소
```

## 공개 범위 세 가지가 실제로 뜻하는 것

| | 링크로 열림 | `/u/<id>/<seq>` | `/u/<id>` 목록 |
|---|---|---|---|
| 비공개 | ✗ | ✗ | ✗ |
| 일부 공개 | **공유를 누른 뒤에만** | ✗ | ✗ |
| 전체 공개 | ✓ | ✓ | ✓ |

**주소가 둘로 갈린 것이 이 표의 전부다.** `/u/<memberId>/<seq>`는 *발견 가능한* 주소라
전체 공개만 답하고, 일부 공개는 `/s/<token>`으로만 열린다.

## 반드시 지켜야 할 것

**일부 공개는 "설정"이 아니라 "공유를 누른 것"이 활성화한다.** `shareToken`이 null인 동안
그 리스트에는 **주소가 아예 없다** — 검사를 빠뜨릴 수 있는 형태가 아니라, 존재하지 않는
것으로 규칙을 강제한다. 토큰은 `ensureShareToken()`이 공유 버튼 요청(`POST
/api/lists/<seq>/share`)에서 발급하고, 멱등이라 지난달에 보낸 링크가 다음 공유에 죽지 않는다.

**그래서 공유 URL을 렌더 시점에 만들지 말 것.** 페이지에 링크를 그려 넣는 순간 아무도
공유하지 않은 리스트가 발행된다. `ListDetailClient`의 `sharable`이 URL이 아니라 boolean인
이유다.

**`readPublicList()`는 `PUBLIC`만 읽는다. `{ in: [LINK, PUBLIC] }`로 되돌리지 말 것.**
`/u/<memberId>/<seq>`는 작은 순차 정수 둘이라, 일부 공개가 여기서 답하면 **찍어보는 것만으로
남이 공유한 적 없는 리스트를 열거할 수 있다.** 그 한 줄 수정이 일부 공개를 통째로 무의미하게
만든다. 같은 이유로 `publicListsOf()`도 `PUBLIC`만 읽는다 — 리스트 하나를 친구에게 공유한
것은 "지금까지 공유한 모든 것의 디렉터리를 발행한다"는 결정이 아니다.

**비공개로 되돌리면 이미 뿌린 링크가 전부 죽는다.** `readListByShareToken()`이 매 요청마다
`visibility`를 다시 읽기 때문이고, 토큰은 지우지 않으므로 **다시 열면 같은 링크가 살아난다**
— 주인이 기대하는 동작이다. 링크를 진짜로 무효화하려면 토큰을 재발급하면 되고(컬럼 모양이
이미 허용한다), 아직 그 라우트는 없다.

**공개 페이지는 이 앱에서 소유자가 아닌 사람에게 소유 행을 보여주는 유일한 곳이다.** 그걸
안전하게 만드는 것은 전부 두 read 함수의 `where` 안에 있다 — 공개범위 검사가 쿼리 조건이라
PRIVATE 리스트는 *읽은 뒤 숨기는* 것이 아니라 **아예 읽히지 않는다.** 이 함수들을 거치지 않고
행을 다시 읽는 폴백을 넣지 말 것. 소유권 술어를 `where`에 두는 이유는 이 저장소가
`Bookmark`에 대해 적어 둔 것과 같다: 읽은 *뒤에* 하는 검사는 나중 수정이 조용히 빠뜨릴 수
있는 검사다.

**`PlaceListEntry`는 하드 삭제하지 않는다.** 찜 해제는 `removedAt`을 찍는다 — 그 행이
사용자가 쓴 `memo`를 들고 있고 그건 다른 어디에도 없기 때문이다. 하드 삭제였다면 별을 한 번
잘못 눌렀다가 되돌리는 것이 메모를 조용히 버리는 일이 된다. 그래서 이 모델은
`HARD_DELETE_ALLOWED`에 **없고**, 런타임 가드가 실제로 거부한다(검증 스크립트가 그걸
확인한다). 재추가는 `removedAt`을 null로 되돌려 **메모를 복원한다** — 원탭 저장이 보내는
`memo: null`이 기존 메모를 덮어쓰지 않는 이유이기도 하다.

**읽기 필터는 두 개이고 함께 움직인다.** 리스트는 `deletedAt`(`liveList`), 항목은
`removedAt`(`liveEntry`). 같은 테이블이 아니고 뜻도 다르다 — 전자는 "리스트를 통째로
버렸다", 후자는 "남겨 둔 리스트 안에서 장소 하나를 뺐다". 항목 필터가 걸리는 자리는 넷:
리스트 상세, 요약 개수(`_count`), 별을 채우는 `listSeqsContaining()`, 공개 페이지.
개수를 세는 곳에서 빠뜨리면 **목록이 상세와 다른 숫자를 광고한다.**

**`memberSeq`는 소프트 삭제된 리스트까지 세어 MAX+1로 발급한다.** 걸러내면 이미 쓰인
번호를 재발급해 첫 삭제 이후 모든 생성이 unique를 위반한다 — `Bookmark.memberSeq`가
적어 둔 바로 그 함정이고, 검증 스크립트가 이것도 확인한다.

**"내 장소"(`isDefault`)는 없어지지도 공개되지도 않는다.** 원탭 저장이 떨어질 곳이므로
항상 존재해야 하고, 사용자가 공개범위 화면을 본 적 없이 암묵적으로 만들어진 리스트라서
공개되면 **고른 적 없는 장소를 발행하는 것**이 된다. 강제는 세 겹이다: 애플리케이션
(`updateList`/`deleteList`), DB의 CHECK(`PlaceList_default_is_private`), 그리고 UI의
비활성화(어포던스일 뿐 강제가 아니다). 하나만 남기지 말 것 — CHECK가 진짜 방어선이다.
"살아 있는 기본 리스트는 최대 하나"는 partial unique index가 지키고, Prisma 스키마 언어로
표현할 수 없어 마이그레이션 raw SQL에만 있다(`Member.phoneHash`와 같은 이유·같은 모양).

**`color`는 hex 패턴이 아니라 allowlist로 검증한다.** 값이 인라인 `background-color`로
렌더되므로 `/^#[0-9a-f]{6}$/`를 통과시키면 여전히 "클라이언트가 고른 문자열이 style
속성에 들어간다". `linkUrl`이 http(s)로 제한되는 것도 SSRF가 아니라 `javascript:` 때문이다
— 서버는 이 URL을 절대 fetch하지 않지만(그래서 호스트 allowlist가 없다), **공유된 리스트를
여는 사람의 브라우저에서 실행될 수 있다.**

**별의 `signedIn`은 "이 리스트의 주인인가"가 아니라 "보는 사람이 로그인했나"다.**
공유된 리스트에서 별은 *보는 사람 자신의* 리스트에 저장하므로, 남의 공개 리스트를 구경하다
장소를 챙기는 것이 바로 그 기능이다. 처음에 `owner`를 넘겼다가 **모든 방문자에게 별이
렌더는 되고 탭은 먹으면서 아무 일도 안 하는** 상태가 됐다(2026-08-30에 브라우저 확인에서
잡음). `ListDetailClient`의 `owner`와 `viewerSignedIn`이 별개 prop인 이유다.

## 아직 없는 것

- **조회 수.** 스크린샷의 눈 아이콘 자리다. 집계·중복 제거·봇 필터링이 딸린 별도 기능이고,
  잘못 만들면 페이지 조회마다 쓰기가 발생하므로 즐겨찾기 본체와 분리해 두었다.
- **공유 링크 무효화 라우트.** `shareToken`을 재발급하면 되고 컬럼 모양이 이미 허용한다.

## 검증

```bash
cd frontend
npx tsx --env-file=.env scripts/verify-place-lists.ts   # 33개 불변조건, 프로브 행을 남긴다
```

라이브 DB에 대고 도는 이유는 확인 대상이 전부 DB 동작이라서다 — partial unique index,
CHECK 제약, 소프트 삭제의 복원, 공개 범위 세 가지의 경계(특히 "공유 누르기 전에는 안 열린다"와
"비공개로 되돌리면 뿌린 링크가 죽는다"), 그리고 런타임 가드가 항목 하드 삭제를 실제로
거부하는지. `verify-soft-delete.ts`와 같이 프로브 행을 정리하지 않고 남긴다(정리하려면 이
저장소가 금지하는 하드 삭제를 해야 한다).
